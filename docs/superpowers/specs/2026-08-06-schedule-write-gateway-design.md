# 시간표 저장 관문 통일 설계

## 목표

시간표 운영 데이터의 저장 방식을 하나의 관문으로 통일한다. 화면과 기존 V1 데이터 형식은 유지하면서, 저장 승인 여부와 서버 반영 완료 여부, 오류 처리 방식을 모든 페이지에서 동일하게 만든다.

이번 단계는 데이터 마이그레이션이 아니다. `swim_students`, `swim_retire`, `swim_enroll`, `swim_mark` 같은 기존 키와 값 형식은 변경하지 않는다.

## 현재 문제

현재 저장 경로는 다음 세 종류가 섞여 있다.

- 여러 키를 묶는 `updateScheduleTx()` 트랜잭션
- `saveJSON()`과 `dbSet()`을 통한 단일 키 저장
- 선생님·데스크 페이지의 `_fb.child(...).set()`, `remove()`, `transaction()` 직접 호출

`dbSet()` 계열은 로컬 캐시를 먼저 바꾸고 서버 저장 완료를 기다리지 않는 호출부가 있다. 반면 자리 이동 같은 작업은 여러 키 트랜잭션을 기다린다. 같은 "저장"이라도 성공 판정과 오류 표시가 화면마다 다르다.

## 검토한 접근

### 접근 A: 기존 V1 위에 공통 저장 관문 추가

기존 데이터 구조와 Firebase 어댑터는 유지하고, 모든 운영 데이터 쓰기를 공통 모듈을 통해 실행한다.

장점:

- 데이터 이전 없이 적용할 수 있다.
- 현재 기능과 화면 결과를 유지하기 쉽다.
- 저장 실패와 중복 저장을 한 곳에서 관찰할 수 있다.
- 이후 V2 전환 시 UI 코드를 다시 고치지 않고 저장 관문 내부만 교체할 수 있다.

단점:

- 큰 JSON 문서를 쓰는 현재 성능 문제는 이번 단계만으로 해결되지 않는다.
- 기존 직접 저장 호출을 이번 작업 범위에서 모두 찾아 교체해야 하므로 변경 파일이 여러 개다.

### 접근 B: V2를 즉시 운영 원본으로 전환

모든 호출부를 원생·배치 단위 V2 문서로 바로 변경한다.

장점은 최종 구조에 빨리 도달하는 것이지만, 메인·선생님·데스크·출석부를 동시에 바꿔야 한다. 현재 운영 규칙을 누락할 위험이 커서 이번 단계에는 사용하지 않는다.

### 접근 C: 직접 저장 호출만 검사

정적 검사로 `_fb.child(...).set()` 같은 호출을 막지만 저장 실행 방식은 그대로 둔다.

변경량은 작지만 서버 완료 확인과 오류 처리 차이는 남는다. 재발 방지 효과가 부족하여 사용하지 않는다.

## 선택한 설계

접근 A를 사용한다.

### 1. 공통 저장 관문

브라우저 전역에서 사용할 수 있는 작은 저장 모듈을 추가한다. 이 모듈은 다음 세 작업만 제공한다.

- 단일 키 저장
- 단일 키 삭제
- 여러 키 트랜잭션

모든 작업은 Promise를 반환하며 Firebase 서버가 성공을 확인한 뒤 완료된다. 실패한 작업은 성공으로 처리하지 않는다.

저장 결과에는 다음 진단 정보가 포함된다.

- 작업 ID
- 작업 종류
- 대상 키
- 시작·완료 시각
- 성공 또는 실패 상태
- 사용자에게 표시할 오류 분류

진단 정보는 개인정보와 원생 데이터 본문을 저장하지 않는다.

### 2. 기존 함수의 호환 계층

`dbSet()`, `dbRemove()`, `saveJSON()`은 즉시 삭제하지 않는다. 기존 호출부가 깨지지 않도록 유지하되 내부 저장은 공통 관문을 사용한다.

새 코드와 수정되는 기존 코드는 Promise를 반환받아 서버 완료까지 기다린다. 원생·담임·등록·퇴원·결석·보강·휴원·출석·대기자·탭·스냅샷을 변경하는 작업의 성공 토스트와 팝업 종료는 저장 완료 이후에만 실행한다.

### 3. 트랜잭션 통합

기존 `updateScheduleTx()`의 업무 로직과 여러 키 원자성은 유지한다. Firebase 직접 트랜잭션 선택 부분만 공통 저장 관문으로 이동한다.

선생님과 데스크 페이지의 별도 트랜잭션 헬퍼도 동일한 관문을 사용한다. 권한 확인은 현재 `SCAuth` 규칙을 그대로 유지한다.

### 4. 로컬 캐시 규칙

서버 저장을 시작하기 전에 로컬 화면을 바꾸는 기존 동작은 호환을 위해 허용할 수 있다. 단, 서버 저장이 실패하면 다음을 보장한다.

- 공통 오류 분류기를 통해 사용자에게 실패를 알린다.
- 해당 키를 서버 값으로 다시 읽어 화면을 복구한다.
- 실패한 로컬 값을 다음 접속에서 운영 원본처럼 사용하지 않는다.

오프라인·스냅샷·타임머신의 읽기 전용 차단 규칙은 유지한다.

### 5. 직접 저장 재발 방지

정적 검사 테스트를 추가한다. 허용된 저장 관문과 Firebase 저장 어댑터 외의 파일에서 다음 패턴이 발견되면 실패한다.

- `_fb.child(...).set()`
- `_fb.child(...).remove()`
- `_fb.child(...).transaction()`
- 운영 키에 대한 직접 Firestore 쓰기

감사기록·복원점 같은 내부 저장도 공통 저수준 실행기를 사용하되, 시간표 변경 감사기록을 다시 생성하지 않도록 `skipAudit` 성격을 유지한다.

## 데이터 흐름

1. 화면이 `이동`, `퇴원`, `출석 저장` 같은 업무 함수를 호출한다.
2. 업무 함수가 기존 상태 검증과 데이터 변경안을 만든다.
3. 공통 저장 관문이 권한·읽기 전용 상태를 확인한다.
4. 공통 저장 관문이 Firebase 저장 또는 트랜잭션을 실행한다.
5. 서버 성공 후 캐시와 화면을 확정하고 성공 UI를 표시한다.
6. 실패하면 오류를 분류하고 서버 값을 다시 읽어 화면을 복구한다.

## 오류 처리

- `permission-denied`: 권한 또는 로그인 오류로 표시한다.
- `unavailable`, 네트워크 오류: 연결 오류로 표시한다.
- `failed-precondition`, 충돌: 최신 데이터 갱신 후 재시도를 안내한다.
- `resource-exhausted`, 크기 제한: 관리자 확인이 필요한 데이터 크기 오류로 표시한다.
- 그 외 오류: 저장 실패로 표시하고 작업 ID를 콘솔 진단에 남긴다.

저장 실패를 성공 토스트로 덮지 않는다. 같은 오류를 저장 관문과 호출부에서 두 번 표시하지 않는다.

## 테스트

테스트를 먼저 작성하고 실패를 확인한 뒤 구현한다.

필수 자동 테스트:

1. 저장 관문이 서버 Promise 완료 전 성공을 반환하지 않는다.
2. 저장 실패가 오류 분류기를 한 번만 호출한다.
3. 여러 키 트랜잭션이 지정된 키만 읽고 쓴다.
4. 트랜잭션 중단은 로컬 상태를 성공으로 확정하지 않는다.
5. 스냅샷·타임머신·서버 로드 실패 상태의 저장이 차단된다.
6. 허용된 모듈 밖의 Firebase 직접 저장 호출을 정적 검사가 차단한다.
7. 기존 단위 테스트와 Firestore 규칙 테스트가 모두 통과한다.

운영 시나리오 확인:

- 원생 정보 수정
- 자리 이동과 자리바꾸기
- 퇴원·등록 예약
- 결석·보강 등록
- 정규·방특 출석 체크
- 대기자와 선생님 정보 수정
- 스냅샷 생성·삭제

## 이번 단계에서 하지 않는 것

- 원생별·슬롯별 Firestore 문서 분할
- V2를 운영 읽기 원본으로 전환
- 하단 기록 생성 규칙 변경
- 화면 디자인 변경
- 과거 데이터 정리 또는 삭제

## 완료 조건

1. 운영 데이터의 Firebase 직접 저장 호출이 허용된 저장 계층 밖에 남지 않는다.
2. 모든 저장 경로가 동일한 오류 분류와 진단 기록을 사용한다.
3. 원생·담임·등록·퇴원·결석·보강·휴원·출석·대기자·탭·스냅샷 변경은 서버 반영 완료 후에만 성공 처리된다.
4. 기존 V1 데이터의 키와 JSON 형식이 바뀌지 않는다.
5. 전체 자동 테스트와 대표 운영 시나리오 테스트가 통과한다.
6. V2 그림자 동기화와 기존 Firestore 권한 규칙 동작이 유지된다.
