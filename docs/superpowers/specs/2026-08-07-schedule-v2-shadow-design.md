# 운영 시간표 V2 그림자 복사 설계

## 목적

가경점과 용암점의 운영 시간표를 V1 원본 그대로 사용하면서, 성공한 시간표 변경을 서버가 V2 작은 문서에도 복사한다. 직원 화면의 읽기량과 저장 지연을 늘리지 않고 V1/V2 불일치를 수집한 뒤, 충분한 검증 후 제한된 V2 읽기로 전환한다.

## 이번 단계의 범위

- 두 지점 모두 적용한다.
- V1은 계속 화면의 읽기·쓰기 원본이다.
- V2는 그림자 복사본이며 운영 화면에서 읽지 않는다.
- 원생 자리, 원생 기본정보, 수강 상태, 담임 배정, 등록·제외·퇴원·휴원·이동예약, 대기자, 결석·보강 표시, 휴관일, 운영 기간과 시간표 설정을 복사한다.
- 출석은 이미 구축한 별도 출석 전환 관문을 유지한다.
- 감사 기록, 복원 지점, 삭제 원본 기록은 이 시간표 그림자 복사에서 제외한다.
- 학부모 요청을 V2 운영 원본으로 바꾸는 작업은 이번 단계에서 하지 않는다.

## 사용하지 않는 방식

### 직원 브라우저에서 전체 변환

기존 `SCV2Shadow`의 개발자 전용 복사 코드를 모든 직원에게 허용하지 않는다. 첫 수정 때 큰 V1 문서를 다시 읽어야 하며, 여러 직원이 동시에 열면 읽기량이 크게 증가한다. 브라우저별로 로드한 키가 다를 때 누락된 데이터를 삭제로 잘못 판단할 위험도 있다.

### 모든 V2 쓰기 권한을 직원에게 개방

직원 계정은 V1 업무 권한만 유지한다. V2 변환과 복사는 Cloud Function 서비스 계정이 담당한다. 따라서 V2 내부 구조가 바뀌어도 직원 권한 규칙을 반복해서 넓히지 않는다.

### V2 즉시 읽기 전환

그림자 복사를 켜는 것만으로 화면을 V2에서 읽지 않는다. 불일치 0건, 동시 수정, 자리 이동과 예약 처리 검증을 통과한 뒤 별도 단계로 진행한다.

## 구조

### 1. 변경 감지

Firestore의 `scheduleStores/{branchId}/kv/{docId}` 변경을 서버 함수가 감지한다. `docId`를 V1 키로 복원하고, 시간표 V2에 영향을 주는 키만 처리한다. 청크 하위 문서는 직접 트리거하지 않으며, 상위 문서의 갱신이 완료된 뒤 저장된 값을 조립해 읽는다.

### 2. 지점별 동기화 요청

변경 함수는 즉시 전체 변환을 수행하지 않고 `scheduleV2/{branchId}/runtime/scheduleSync`에 다음 내용을 병합한다.

- 변경된 V1 키 집합
- 마지막 요청 시각
- 요청 세대 번호
- 처리 상태

한 번의 자리 이동이 여러 V1 키를 변경해도 요청 문서에서 합쳐진다. 이미 처리 중이면 새 세대 번호를 남겨 현재 처리가 끝난 뒤 한 번 더 실행한다.

### 3. 서버 처리기

처리기는 지점별로 하나만 실행되도록 잠금을 얻는다. 변경 키를 V2 컬렉션 범위로 변환하고 필요한 V1 키만 읽는다. 서로 연관된 변경은 한 묶음으로 처리한다.

| V1 변경 | V2 범위 |
| --- | --- |
| 원생 시간표 | `people`, `enrollments`, `placements` |
| 담임 | `teacherAssignments` |
| 등록·제외·휴원·이동 | `reservations` 및 관련 원생 범위 |
| 대기자 | `waitlistEntries` |
| 결석·보강 표시 | `classMarks` |
| 휴관·운영 기간·설정 | `calendarClosures`, `schedulePeriods`, `scheduleSettings`, `disabledSlots` |
| 탭·폴더·교사정보 | `tabs`, `tabFolders`, `teacherProfiles`, `archivedTabs` |

정규반과 방특반은 `tabId`와 `courseType`으로 분리한다. 이름과 전화번호가 같아도 정규/방특 수강과 자리 데이터는 별개이며, 동일 원생의 `personId`만 공유한다. 형제는 이름이 다르므로 같은 전화번호여도 서로 다른 `personId`를 유지한다.

### 4. 세대와 원자성

현재 검증된 그림자 세대를 계속 사용한다. 한 V1 업무가 여러 키를 바꿀 경우 V2에서는 새 요청 세대의 모든 쓰기가 성공한 뒤에만 `appliedRevision`을 올린다. 일부 컬렉션 저장이 실패하면 해당 요청은 완료로 표시하지 않고 재시도 대상으로 둔다.

V1 저장은 이미 성공했으므로 V2 오류를 직원에게 저장 실패로 표시하지 않는다. 다만 개발자 진단에는 지점, 변경 키, 실패 범위, 요청 세대와 시각을 남긴다. 원생 이름이나 전화번호는 진단 메시지에 넣지 않는다.

### 5. 비교

V2 저장 후 변경된 범위만 V1에서 다시 정규화하여 다음을 비교한다.

- 문서 개수
- 문서 ID 집합
- 정규화한 내용 해시
- 참조 무결성: 자리의 `personId`, `enrollmentId`, 탭과 담임 참조

불일치가 있으면 V1은 그대로 유지하고 `scheduleV2/{branchId}/alerts`에 유형별 경고를 합쳐 기록한다. 같은 오류를 매번 새 문서로 늘리지 않는다.

## 초기 기준점 갱신

운영 그림자 복사를 켜기 전에 두 지점 V1을 서버에서 읽어 최신 V2 세대를 한 번 완전 동기화하고 검증한다. 기존 세대를 바로 덮어쓰지 않고 새 기준 세대를 만든 뒤 검증이 끝난 경우에만 시간표 그림자 설정이 그 세대를 가리키게 한다.

초기 복사 중에도 V1 운영은 계속된다. 복사 시작 이후 발생한 변경은 요청 문서에 쌓았다가 기준 세대 생성 후 다시 적용하여 복사 도중의 수정이 빠지지 않게 한다.

## 전환 상태

시간표는 지점별로 다음 상태를 갖는다.

1. `v1`: V1만 운영한다.
2. `shadow`: V1 원본, V2 비동기 복사와 범위 비교.
3. `verify`: V1 원본, V2 복사 완료와 비교 완료를 운영 진단에서 강하게 확인.
4. `v2-read`: 지정된 개발자·데스크 계정만 V2에서 읽고 V1에도 복구본을 쓴다.
5. `v2`: V2가 운영 원본이며 V1은 제한된 기간 동안 복구본으로 보관한다.

이번 구현은 두 지점을 `shadow`까지 전환한다.

## 복구

- 설정을 `v1`으로 바꾸면 신규 V2 그림자 요청을 중단한다.
- V1 문서는 그림자 복사 과정에서 수정하거나 삭제하지 않는다.
- 실패한 V2 세대는 운영 읽기에 사용하지 않는다.
- V2 문서 정리가 필요해도 V1과 출석·감사 기록은 삭제하지 않는다.
- 설정 변경 전후 값과 대상 세대를 시스템 메타데이터에 기록한다.

## 테스트

### 자동 테스트

- V1 키가 올바른 V2 범위로 매핑된다.
- 청크 문서를 포함한 V1 값을 서버에서 동일하게 복원한다.
- 여러 키 변경이 지점별 요청 하나로 합쳐진다.
- 처리 중 추가 변경이 오면 다음 실행으로 이어진다.
- 정규·방특과 형제 ID가 섞이지 않는다.
- 자리 이동, 시간 변경, 반 변경, 등록·퇴원 예약이 관련 문서를 함께 갱신한다.
- V2 오류가 V1 저장 결과를 실패로 바꾸지 않는다.
- 불일치는 개인정보 없이 하나의 경고로 누적된다.
- V1 복귀 후 신규 V2 쓰기가 중단된다.

### 운영 확인

- 두 지점에서 원생 등록, 이동, 제외, 퇴원, 대기자와 담임 변경을 각각 수행한다.
- 여러 기기에서 같은 시간대에 수정한 뒤 V1/V2 내용이 일치하는지 확인한다.
- 정규반과 방특반을 모두 확인한다.
- 최소 한 운영 주기 동안 불일치 0건을 확인한 뒤 `verify`로 이동한다.

## 실제 V2 읽기 전환 조건

- 두 지점의 최근 전체 기준점 검증 성공
- 그림자 처리 대기 0건
- 미해결 불일치 0건
- 모든 주요 수정 시나리오 자동 테스트 통과
- 개발자 계정의 V2 읽기 시험 통과
- 데스크 한 계정의 제한 운영 시험 통과
- V1 복귀 시험 통과

조건 중 하나라도 충족하지 않으면 실제 V2 읽기로 넘어가지 않는다.
