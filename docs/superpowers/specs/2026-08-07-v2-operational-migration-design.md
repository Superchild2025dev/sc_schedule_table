# V2 운영 데이터 단계 전환 설계

## 목적

현재 V1의 큰 JSON 문서를 실제 운영 중인 기능별 작은 문서로 분리한다. 데이터 누락이나 화면 회귀 없이 V2를 최종 운영 원본으로 전환하고, 전환 중 문제가 발견되면 V1으로 되돌아갈 수 있게 한다.

이번 설계는 전체 전환 순서와 공통 안전장치를 정의한다. 첫 구현 범위는 정규반·방학특강 출석부다. 원생 시간표와 나머지 업무 데이터는 출석부 전환이 검증된 뒤 같은 절차로 별도 구현한다.

## 현재 문제

- 한 명의 출석, 결석 또는 자리 변경도 큰 V1 JSON 문서 전체를 읽고 다시 저장한다.
- 여러 기기가 동시에 수정하면 서로 다른 시점의 큰 객체가 충돌할 가능성이 있다.
- 원생, 배치, 출석, 예약, 기록의 책임이 전역 변수와 큰 파일에 섞여 있다.
- V2는 작은 문서로 변환되어 있지만 현재는 개발자용 그림자 복사본이므로 운영 효율 개선에 직접 사용되지 않는다.
- V1과 V2를 영구적으로 동시에 운영하면 비용과 유지보수 지점이 두 배가 된다.

## 접근법 비교

### 1. V1을 다시 분리

기존 `swim_attendance`, `swim_students` 같은 키 옆에 날짜별·원생별 V1 키를 추가한다. 구현은 익숙하지만 기존 V2와 중복되는 세 번째 구조가 생긴다. 장기 유지보수에 불리하므로 사용하지 않는다.

### 2. V2 전체 즉시 전환

모든 화면과 저장을 한 번에 V2로 바꾼다. 최종 구조에는 빨리 도달하지만 출석, 자리 이동, 퇴원, 보강, 권한을 동시에 수정해야 하므로 장애 원인을 분리하기 어렵다. 사용하지 않는다.

### 3. 업무 영역별 단계 전환 - 선택

V2를 최종 원본으로 정하고 출석부부터 한 영역씩 전환한다. 각 영역은 `복사 → 검증 → 그림자 쓰기 → 제한된 읽기 전환 → 전체 전환 → V1 종료` 단계를 거친다. 변경 범위와 복구 범위가 작아 가장 안전하다.

## 최종 데이터 경계

V2 문서는 다음 책임으로 분리한다.

- `people`: 이름, 전화번호처럼 사람에게 귀속되는 정보
- `enrollments`: 정규반·방특 과정 참여 정보
- `placements`: 요일, 시간, 레인, 담당 선생님과 같은 자리 정보
- `attendanceRecords`: 시간표 범위와 날짜별 출석 상태
- `attendanceGuests`: 날짜별 출석부 추가 원생
- `reservations`: 등록, 제외, 이동, 휴원 예약
- `classMarks`: 결석, 보강, 샘플, 의무보강 표시
- `retirementRecords`: 퇴원 원본 기록
- `deskRecords`: 데스크가 편집하는 하단 기록

화면 코드는 이 저장 위치를 직접 알지 않는다. `SCOperationalStore`라는 작은 관문을 통해 읽고 저장한다. 관문 내부만 V1 또는 V2를 선택하게 하여 이후 데이터 구조가 바뀌어도 화면 함수를 다시 뜯지 않는다.

## 전환 상태

각 지점과 업무 영역은 다음 상태 중 하나를 가진다.

1. `v1`: V1만 운영한다.
2. `shadow`: V1이 원본이며 성공한 변경을 V2에도 복사하고 결과를 비교한다.
3. `verify`: V1이 원본이며 V1·V2 저장 완료와 내용 일치를 모두 확인한다.
4. `v2-read`: 화면은 V2를 읽고 저장은 V2에 먼저 반영한 뒤 V1 복구본도 갱신한다.
5. `v2`: V2만 운영하고 V1은 읽기 전용 백업으로 보관한다.

상태는 지점과 영역별로 독립적이다. 예를 들어 용암점 출석부만 `v2-read`로 두고 가경점 및 원생 시간표는 `v1`으로 유지할 수 있다.

상태 변경은 개발자 계정만 할 수 있다. 선생님과 데스크 화면에는 전환 제어 UI를 노출하지 않는다.

## 첫 전환 영역: 출석부

### 저장 단위

정규반과 방특반을 섞지 않는다. 기존 V2 변환 형식을 그대로 사용하여 출석은 `시간표 범위 + 날짜 + 원생 자리`별 개별 `attendanceRecords` 문서로 관리한다. 출석부 추가 원생은 `attendanceGuests` 개별 문서로 관리한다. 새로운 날짜 묶음 구조를 추가하지 않는다.

출석 문서 한 건에는 다음 정보만 둔다.

- 날짜
- 시간표 범위 ID
- 원생 ID, 등록 ID 또는 출석부 추가 원생 ID
- 시간, 요일, 레인, 자리와 주·보조 원생 구분
- 출석 또는 결석 상태
- 수정 시각
- 수정 계정 식별값

이름, 전화번호, 승하차 위치를 출석 문서에 복제하지 않는다. 화면 표시가 필요하면 원생·배치 정보에서 조합한다. 과거 출석부 스냅샷은 당시 이름과 반을 보존해야 하므로 기존 날짜 스냅샷 영역을 유지한다.

### 읽기

- 출석부를 열기 전에는 출석 문서를 읽지 않는다.
- 정규 출석부는 화면에 표시하는 월요일부터 토요일까지 최대 6개 날짜 범위의 개별 출석 문서만 읽는다.
- 방특 출석부는 해당 기간의 월요일부터 금요일까지 최대 5개 날짜 범위의 개별 출석 문서만 읽는다.
- 조회는 `tabId + date` 조건을 사용하며 필요한 Firestore 복합 인덱스를 저장소 설정에 명시한다.
- 운영월 경계를 넘는 주는 날짜별 기준 시간표를 각각 준비한 뒤 렌더한다.
- 과거 날짜는 기존 날짜 스냅샷을 우선 사용한다.

### 쓰기

- 준비되지 않은 날짜에는 저장하지 않는다.
- 한 명 체크는 해당 출석 문서 한 건만 트랜잭션으로 수정한다.
- 일괄 체크는 해당 날짜의 개별 출석 문서를 하나의 Firestore 배치로 수정한다.
- 추가 원생 등록·삭제는 해당 `attendanceGuests` 문서 한 건만 처리한다.
- 서버 저장 완료 전 성공 메시지를 표시하지 않는다.

## 복사와 검증

V1 출석 키를 날짜와 시간표 범위별 V2 문서로 변환한다. 변환은 V1을 읽기만 하며 V1 값을 수정하거나 삭제하지 않는다.

검증은 단순 문서 개수만 비교하지 않는다.

- 정규·방특 범위별 날짜 수
- 날짜별 출석 문서와 학생 ID 수
- 출석·결석 상태 수
- 추가 원생 수
- 정규화한 내용의 해시
- 변환하지 못한 키와 중복 학생 ID

하나라도 다르면 해당 지점 출석부를 `v2-read`로 바꿀 수 없다. 불일치 내용은 원생 이름이나 전화번호 없이 범위, 날짜, 개수, 오류 종류만 개발자 진단에 남긴다.

## 동시 수정

- V1 저장은 기존 서버 트랜잭션을 유지하고 V2 개별 출석 저장은 대상 문서 트랜잭션을 사용한다.
- 같은 날짜를 두 기기가 수정해도 다른 원생이면 서로 다른 문서이므로 충돌하지 않는다.
- 같은 원생을 동시에 수정할 때만 해당 문서 트랜잭션 순서에 따라 최신 서버 결과가 남는다.
- 더 늦게 끝난 오래된 화면 요청은 현재 화면을 다시 그리지 않는다.
- V2 저장 실패 시 V1 운영은 유지하고 전환 상태를 자동으로 `v1`으로 낮추지 않는다. 대신 해당 영역의 V2 전환을 차단하고 개발자 진단에 알린다.

## 권한

- 선생님은 본인 지점의 정규·방특 출석 문서만 읽고 쓸 수 있다.
- 데스크와 관리자는 본인 지점의 출석 문서를 읽고 쓸 수 있다.
- 다른 지점 문서는 읽거나 쓸 수 없다.
- 전환 설정, 검증 결과, 마이그레이션 메타데이터는 개발자 계정만 수정할 수 있다.
- Firebase 규칙은 현재 단일 권한 매니페스트에서 생성하며 수기 복사본을 만들지 않는다.

## 실패와 복구

- `shadow`와 `verify`에서는 V1이 계속 운영 원본이므로 V2 오류가 출석 체크를 막지 않는다.
- `v2-read`에서 V2 읽기에 실패하면 같은 세션에서 임의로 V1과 섞지 않는다. 출석 저장을 차단하고 명확한 재시도 안내를 표시한다.
- 개발자는 영역 상태를 `v1`로 되돌린 뒤 새로고침하여 V1으로 복구할 수 있다.
- V1 문서는 모든 출석 시나리오 검증과 운영 확인이 끝날 때까지 삭제하지 않는다.
- 자동 복구가 데이터를 어느 쪽이 최신인지 추측해 덮어쓰지 않는다.

## 화면 동작

기존 시간표와 출석부 UI는 바꾸지 않는다.

- 로딩 중 현재 표를 유지한다.
- 필요한 날짜가 모두 준비된 뒤 한 번 렌더한다.
- 로딩 중 체크를 누르면 저장하지 않고 준비 중 안내를 표시한다.
- 전환 상태와 V2 경고는 개발자 설정 화면에서만 보인다.

## 구현 순서

1. 기존 V2 출석 변환 결과를 운영 읽기·쓰기에 사용할 수 있는 순수 어댑터를 만든다.
2. V1 출석을 V2 개별 출석 문서로 복사하고 내용까지 검증하는 도구를 만든다.
3. `SCOperationalStore`에 출석 읽기·쓰기 인터페이스를 추가한다.
4. 개발자 계정과 용암점에서 `shadow` 상태로 비교한다.
5. 정규·방특 개별 체크, 일괄 체크, 추가 원생, 월 경계, 과거 출석을 검증한다.
6. 용암점을 `v2-read`로 전환하고 문제 없을 때 가경점도 전환한다.
7. 두 지점 출석부를 `v2`로 확정한 뒤 다음 영역인 원생·담임 전환 설계를 시작한다.

## 후속 영역 순서

1. 원생·담임·자리 배치
2. 등록·제외·퇴원·이동·휴원 예약
3. 결석·보강·샘플·의무보강 표시
4. 퇴원 원본 기록과 데스크 하단 기록
5. 학부모 요청은 현재 보류 상태를 유지하며 별도 승인 후 전환

각 후속 영역은 출석부와 동일하게 복사, 내용 검증, 그림자 쓰기, 제한 전환, 전체 전환 절차를 반복한다.

## 테스트 기준

### 순수 데이터 테스트

- V1 정규·방특 출석이 개별 V2 출석 문서로 손실 없이 변환된다.
- 같은 이름·전화번호의 정규반과 방특반 출석 범위가 섞이지 않는다.
- 형제처럼 전화번호가 같고 이름이 다른 원생은 별도 ID로 유지된다.
- 잘못된 출석 키, 없는 학생 ID, 중복 항목은 조용히 버리지 않고 전환을 차단한다.

### 저장 테스트

- 한 명 체크가 다른 학생 상태를 지우지 않는다.
- 두 기기의 서로 다른 학생 체크가 모두 남는다.
- 일괄 체크와 개별 수정이 서로 다른 원생 문서를 유실하지 않는다.
- V2 실패가 `shadow` 상태의 V1 출석 저장을 실패로 표시하지 않는다.
- `v2-read` 준비 전에는 출석 저장이 차단된다.

### 화면 회귀 테스트

- 정규·방특 개별 출석
- 정규·방특 일괄 출석
- 출석 해제와 결석 체크
- 출석부 추가 원생 등록·삭제
- 운영월 경계를 넘는 주
- 과거 출석부와 날짜 스냅샷
- 선생님, 데스크, 관리자 권한
- 빠른 날짜 전환과 탭 전환

### 완료 기준

- V1과 V2의 정규화한 출석 내용이 두 지점에서 일치한다.
- 변환 불가 및 중복 항목이 0건이다.
- 모든 자동 테스트와 Firebase 규칙 에뮬레이터 테스트가 통과한다.
- 개발자 진단에 개인정보 본문이 남지 않는다.
- V1 복구 절차를 로컬 환경에서 실제로 검증한다.

## 범위 밖

- 이번 첫 구현에서 원생 시간표, 등록·퇴원, 결석·보강을 V2 운영 원본으로 바꾸지 않는다.
- 기존 UI 디자인을 변경하지 않는다.
- V1 데이터를 삭제하지 않는다.
- 학부모 요청 구조를 변경하지 않는다.
