# V2 운영 동시성 및 복구 설계

## 목적

V2 데이터 보호 장치는 유지하면서, 일반적인 원생 수정과 출석 저장을 운영 권한 변경으로 오인해 화면 전체를 새로고침하거나 장시간 읽기 전용으로 만드는 문제를 제거한다.

이 설계의 성공 기준은 다음과 같다.

- 한 사용자의 일반 저장이 다른 사용자의 페이지를 새로고침하지 않는다.
- 서로 다른 학생, 자리, 출석 기록은 동시에 저장할 수 있다.
- 같은 대상을 동시에 수정한 경우에만 한쪽을 충돌로 처리하고 최신 데이터를 다시 보여준다.
- 최초 운영 설정 조회가 일시적으로 실패해도 연결 회복 후 자동으로 정상화된다.
- 탭 전환과 독립적인 보조 조회가 진행 중인 저장 또는 다른 조회를 무효화하지 않는다.
- 서버에 이미 성공한 저장을 화면에서 실패로 안내하지 않는다.
- 세대 전환, 권한 변경, 불완전한 서버 작업은 계속 차단한다.

## 확인된 근본 원인

### 권한 포인터와 데이터 revision의 혼용

현재 `mode`, `generationId`, `epoch`, `revision` 전체를 하나의 운영 권한 지문으로 사용한다. 일반 저장도 지점 전역 `revision`을 증가시키므로 다른 기기의 정상적인 데이터 변경이 운영 권한 변경으로 판단된다.

그 결과 다른 기기는 선택 데이터 갱신 대신 페이지 전체 새로고침을 요청한다. 여러 사용자가 저장하면 새로고침과 세션 잠금이 반복될 수 있다.

### 지점 전역 쓰기 직렬화

시간표와 출석을 포함한 모든 저장이 하나의 지점 전역 revision을 공유한다. 서버는 요청의 `beforeRevision`이 현재 revision과 다르면 저장을 거부한다.

시간표 저장은 한 번만 변경 의도를 재적용하고, 출석 저장은 충돌 재적용을 하지 않는다. 따라서 서로 다른 대상을 수정해도 동시 저장 수가 늘어나면 일부 요청이 실패한다.

### 실패한 초기 설정의 영구 캐시

최초 설정 조회 실패 결과를 완료된 `readyPromise`로 보관한다. 실패 후 설정 listener를 시작하지 않으므로 네트워크가 회복되어도 같은 페이지에서는 정상 권한을 다시 확인하지 않는다.

### 전역 조회 취소 번호

활성 탭 조회, 보조 조회, 저장 준비 조회가 단일 selection version을 공유한다. 서로 관계없는 새 조회가 이전 정상 조회를 stale 결과로 만들 수 있다.

### 전체 generation 검증

작은 변경도 generation 전체 collection을 읽고 모든 도메인의 무결성을 검사한다. 현재 수정과 관계없는 과거 기록 또는 스냅샷 문제 때문에 정상 저장까지 막힐 수 있다.

## 운영 원칙

### 권한 버전과 데이터 버전 분리

운영 권한 지문은 다음 값만 사용한다.

- `branchId`
- `mode`
- `generationId`
- `epoch`

`revision`은 데이터 동시성 제어와 최신 데이터 감지에만 사용한다. revision 변경만으로 페이지를 새로고침하지 않는다.

`mode`, `generationId`, `epoch` 중 하나가 바뀐 경우에는 기존 화면이 다른 데이터 권한을 가리킬 수 있으므로 현재처럼 전체 화면을 안전하게 재시작한다.

### 데이터 변경 수신

외부 revision 변경을 받으면 현재 화면에서 사용 중인 선택 범위만 무효화하고 다시 조회한다. 사용자가 입력 중인 모달, 스크롤 위치, 활성 탭은 유지한다.

원격 변경이 현재 편집 대상과 무관하면 조용히 새 데이터를 반영한다. 현재 편집 대상과 겹치면 저장 시점의 대상 digest로 충돌 여부를 판단한다.

### 대상 단위 충돌

지점 전역 revision은 서버 작업 순서와 복구 기록을 위해 유지한다. 그러나 stale revision만으로 요청을 최종 거부하지 않는다.

서버는 요청에 포함된 각 문서의 `beforeExists`와 `beforeDigest`를 확인한다.

- 대상 문서가 바뀌지 않았으면 최신 지점 revision 위에서 요청을 다시 적용한다.
- 대상 문서가 바뀌었으면 `aborted`로 반환한다.
- 세대, epoch, mode가 바뀌었으면 `failed-precondition`으로 차단한다.

브라우저는 `aborted`를 받은 경우 최신 선택 범위를 한 번 다시 읽고 원래 변경 의도를 재적용한다. 같은 대상이 실제로 달라졌다면 덮어쓰지 않고 충돌 안내와 최신 값을 보여준다.

재시도 횟수는 최초 요청을 포함해 최대 3회로 제한한다. 같은 `operationId`를 유지해 응답 유실 시 중복 저장을 방지한다.

### 출석 저장

출석은 화면에 보이는 전체 map을 기준으로 다시 저장하지 않는다. 변경된 출석 record 또는 guest record 목록을 요청 의도로 만든다.

서버는 해당 record만 검사하고 저장한다. 다른 날짜나 다른 학생의 출석 변경은 충돌하지 않는다. 같은 날짜, 같은 자리의 동일 record가 동시에 바뀐 경우에만 최신 값을 다시 읽고 사용자에게 충돌을 알린다.

### 초기 연결 복구

최초 운영 설정 조회가 실패하면 오래된 V1 데이터를 운영 데이터처럼 표시하지 않는다.

- 짧은 지수 백오프로 설정 조회를 최대 3회 재시도한다.
- listener를 사용할 수 있으면 조회 실패와 관계없이 즉시 listener를 시작한다.
- 연결 회복 전에는 마지막으로 확인된 정상 화면이 있으면 그대로 유지하고 저장만 막는다.
- 정상 화면이 없으면 명확한 연결 대기 상태를 표시한다.
- 정상 설정이 도착하면 새로고침 없이 해당 선택 범위를 로드하고 저장을 다시 허용한다.

### 조회 범위 분리

조회 취소 토큰은 owner와 선택 범위별로 관리한다.

- 활성 시간표
- 출석부
- 보조 모달
- 내보내기
- 저장 준비 조회

같은 owner에서 더 최신 요청이 시작된 경우에만 이전 요청을 stale 처리한다. 다른 owner의 요청은 서로 취소하지 않는다.

### 저장 성공 후 UI 이동

서버가 저장 성공을 반환하면 그 작업은 성공으로 확정한다. 응답 도착 전에 사용자가 탭을 바꿨다는 이유로 저장 성공을 실패로 바꾸지 않는다.

이전 탭의 데이터는 현재 화면에 주입하지 않으며, 해당 탭 캐시만 무효화한다. 사용자가 다시 탭을 열면 최신 데이터를 조회한다.

### 부분 무결성 검증

변경 계획을 만들 때 수정 대상과 직접 연결된 collection만 읽고 검사한다.

- 원생 배치: people, enrollments, placements, 관련 예약
- 선생님 배치: teacherAssignments, 관련 tab
- 출석: attendanceRecords 또는 attendanceGuests
- 결석 및 보강: classMarks와 관련 enrollment
- 탭과 기간: tabs 및 직접 참조되는 설정

generation 전체 검증은 전환, 백업 검증, 개발자 점검에서만 수행한다. 일반 저장에서는 변경 대상의 참조 무결성과 문서 크기만 검사한다.

## 유지할 안전장치

- 인증 및 역할 검사
- 지점 접근 정책
- mode, generation, epoch 일치 검사
- operation ID 멱등성
- 문서별 before digest 충돌 검사
- 서버 전용 쓰기
- 불완전 작업 fence 및 복구 manifest
- 개인정보가 없는 제한된 진단 기록
- 동일 대상 충돌 시 자동 덮어쓰기 금지

## 제거하거나 축소할 안전장치

- 일반 revision 변경 시 전체 페이지 새로고침
- 최초 설정 조회 실패의 영구 읽기 전용 캐시
- 모든 조회가 공유하는 전역 stale token
- 출석 전체 map 재저장
- 작은 변경의 generation 전체 검증
- 저장 성공 후 화면 컨텍스트 변경을 실패로 변환하는 검사
- 서로 다른 문서 충돌에 대한 단일 재시도 제한

## 오류 처리

사용자에게는 다음 세 종류만 구분해 안내한다.

1. 연결 대기: 자동으로 다시 연결하며 현재 입력은 유지한다.
2. 동일 대상 충돌: 최신 내용을 보여주고 사용자가 다시 확인하도록 한다.
3. 운영 권한 변경: mode, generation, epoch 변경 때만 화면을 다시 연다.

내부 진단에는 지점, operation type, 대상 문서 수, 시도 횟수, 오류 코드만 남긴다. 학생 이름, 전화번호, 출석 값은 남기지 않는다.

## 테스트 전략

### 권한 및 새로고침

- 외부 revision 증가만으로 새로고침하지 않는다.
- mode, generation, epoch 변경은 한 번만 새로고침한다.
- 새로고침 호출 실패 시 listener와 복구 경로가 남아 있다.

### 초기 연결

- 최초 조회 실패 후 두 번째 조회 성공으로 쓰기 권한이 자동 복구된다.
- listener가 먼저 정상 설정을 받는 경우에도 자동 복구된다.
- V2 권한을 확인하지 못한 상태에서 V1 데이터를 운영 데이터로 표시하지 않는다.

### 시간표 동시성

- 서로 다른 학생 3건을 동시에 수정해도 모두 저장된다.
- 원생과 선생님을 동시에 수정해도 모두 저장된다.
- 같은 학생을 동시에 수정하면 한쪽만 저장되고 다른 쪽은 충돌을 받는다.
- 충돌 재시도 중 mode, generation, epoch가 바뀌면 저장을 중단한다.

### 출석 동시성

- 서로 다른 출석 record 2건을 동시에 저장해도 모두 반영된다.
- 정규반과 방특 출석을 동시에 저장해도 서로 영향을 주지 않는다.
- 같은 출석 record를 동시에 수정하면 최신 데이터가 보존되고 충돌을 알린다.

### 화면 이동 및 조회

- 저장 중 탭을 바꿔도 서버 저장 성공은 성공으로 유지된다.
- 활성 시간표 조회와 보조 모달 조회가 서로 취소되지 않는다.
- 동일 owner의 늦은 응답만 폐기된다.

### 부분 검증

- 무관한 과거 snapshot 오류가 현재 출석 저장을 막지 않는다.
- 잘못된 대상 문서 또는 끊어진 직접 참조는 저장을 차단한다.
- 전환 전 전체 검증은 기존과 동일하게 모든 generation을 검사한다.

## 적용 순서

1. 실패 재현 테스트를 추가한다.
2. 권한 지문에서 revision을 분리한다.
3. 초기 연결을 재시도 가능한 상태 기계로 바꾼다.
4. 조회 취소 토큰을 owner별로 분리한다.
5. 시간표 서버 저장을 대상 문서 충돌 방식으로 바꾼다.
6. 출석 저장을 record 단위 변경 요청으로 바꾼다.
7. 일반 저장의 전체 generation 검증을 관련 도메인 검증으로 축소한다.
8. 가경점과 용암점에서 정규반, 방특, 출석, 결석, 보강 회귀 테스트를 실행한다.

각 단계는 독립 테스트를 통과한 뒤 다음 단계로 넘어간다. 단계 중 하나가 실패하면 이전 단계까지의 동작을 유지하며 V2 전체 전환은 진행하지 않는다.
